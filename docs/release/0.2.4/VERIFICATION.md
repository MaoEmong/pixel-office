# Windows 0.2.4 배포 검증

2026-10-31 기준입니다. 진행 중인 MES 앱과 분리한 E드라이브의 환경에서 검사합니다. GitHub 자동 검사 작업은 설정돼 있지 않으므로 로컬 검사와 배포 파일 검사 결과를 구분해 기록합니다.

## 소스와 복구 검사

- 최종 서버 전체 1,609 통과·17 제외·실패 0, 형식 검사 통과.
- PC 화면 전체 996 통과·1 제외·실패 0, 분석 검사 지적 없음. 사용자 설정과 분리한 E드라이브의 데이터 경로로 검사했습니다.
- 지시·보고를 전송 전에 저장하고, 담당자 재시작·저장소 재열기 뒤 대기 지시가 유지되는지 확인했습니다. 접수 불확실·저장 실패·연결 종료·직접 입력 보호·명시적 취소·완료된 업무 재실행 방지를 검사합니다.
- 배포 전 검토에서 접수 신호 없이 재시작한 AI의 대화 파일 위치를 찾지 못하는 누락을 발견했습니다. 경로를 검사에서 직접 넣던 처리를 제거하고, Claude 재시작과 새 신호 없는 Codex 재시작을 재현했습니다. 수정 전 두 경우 실패, 수정 후 관련 14개 통과입니다.
- 해당 멤버의 세션 폴더 안에서만 정해진 깊이·최대 4,096개 항목으로 기록 경로를 찾습니다. 보관된 Codex 기록·다른 대화 구분·경로 이탈·연결 폴더 거절도 확인했습니다. 실제 접수 확인은 최대 2MiB의 끝부분에서 정확한 표식이 있는 사용자 메시지만 대상으로 합니다.
- 한도·로그인·모델 준비, 시작 중 폴더 확인, 오래된 사용량 정보와 별도 사용량 확인 명령의 접수 누락도 검사했습니다. 허가나 한도 중지를 자동으로 우회하지 않습니다.
- 별도 실행·감시와 결과 대기 상태를 확인하고, 종료 신호가 없으면 성공으로 처리하지 않는지 검사했습니다. 오래 걸리는 검사·빌드를 자동 취소하거나 반복하지 않습니다.

## 실제 작업 확인과 배포 파일의 구분

이번 배포의 선행 로컬 수정본을 적용할 때 기존 AI 대화 7개, 업무 270건, 대화 기록 647건, 질문·허가 이력 126건, 완료 6단계, 원본 대화 파일 10개와 보조 기록을 비교해 보존을 확인했습니다. 적용 대기 해제 뒤 실제 지시 접수·담당자 전달·백엔드 수정과 진행 보고가 이어졌습니다. 재연결 중 일시적인 Codex 연결 오류도 같은 대화로 자동 복구됐습니다.

선행 수정에서는 E의 별도 실제 Claude·Codex 환경에서 각 두 번의 접수 신호를 누락시킨 뒤, 기록을 근거로 중복 요청 없이 복구함을 확인했습니다. Codex 검사 종료 정리에서 기존에 알려진 `AttachConsole failed` 경고가 나타났으며 접수 복구와 저장 종료는 완료됐습니다. 이 결과를 모든 터미널 종료 경로에 경고가 없다는 뜻으로 해석하지 않습니다.

배포 전 추가한 대화 경로 탐색 보완은 위의 별도 재시작 검사로 확인합니다. **새 배포를 위해 현재 진행 중인 MES 앱과 AI를 다시 시작하거나 종료하지 않습니다.** 로컬 적용 확인, 최종 ZIP 검사와 사용자 MES 전체 완료는 서로 다릅니다.

- 파일: `PixelOffice-0.2.4-windows-x64.zip`, 크기 71,243,268바이트.
- SHA256: `f947e72f4005c41eed8cd7b60646c88a7e99aec09964c76d23937c764f26217b`
- 빌드 기준 커밋: `92fc71996aa7f4e59d7846a6a9ebd62cde2aff5d`. 빌드 입력의 미커밋 수정 없음.
- Windows 실행 파일·내부 프로그램을 E의 새 폴더에서 빌드했습니다. ZIP을 E의 새 폴더에 다시 풀어 구성품 1,943개와 전체 파일 목록·해시를 대조했습니다. 앱·manifest·내부 프로그램 버전은 0.2.4이며 원본 소스·개발 파일·DB·인증 파일을 제외했습니다.
- 실제 Windows 앱의 별도 사용자·데이터·포트에서 시작, 원격 화면, 미설치 AI 안내, 정상 종료, 설정 보존과 서버 자동 복구 등 10항목을 통과했습니다. 실제 AI 모델 요청 없이 실행한 검사입니다.
- 구형 형식의 대화 5,000개를 변환 전 백업하고 전체 페이지·변경분 전달·두 번 시작 뒤 보존을 확인했습니다. 적용 대기 설정과 명시적 대기 해제도 검사했습니다.
- 포장된 서버의 실제 종료 신호로 미완료 진행 보고·추가 배정·결과 대기 관계가 유지되며, 턴 종료만으로 업무를 완료하지 않는지 확인했습니다.
- 최종 포장 서버를 별도로 시작하고 실제 Codex에서 저장된 대화와 정확한 접수 표식을 복원했습니다. 새 접수 신호나 원래 요청 재전송 없이 접수를 확인하고 기존 대화 ID·원본 대화 내용을 유지했습니다. 새 모델 요청은 보내지 않았고 진행 중인 MES는 변경하지 않았습니다.
- 포장된 서버의 문서 읽기·저장·충돌/경로 보호, 파일 저장·확인 후 복구·타임라인, Windows 암호화 키 보관과 확인 없는 전체 허가 거절, 나중에 등록한 키의 과거 조회 가림 및 재시작 보존을 검사했습니다.
- 실제 Windows 출력 연결 회귀 검사 4개 통과. 공개 문서와 배포 파일에서 검사 대상으로 둔 개인 식별 문자열은 발견되지 않았습니다. 모든 비밀값의 부재를 보증하는 검사는 아닙니다.

최종 ZIP은 위 커밋으로 만들었으며, 이후 이 검증 문서와 공개 안내 정리는 실행 파일을 변경하지 않습니다. 업로드한 파일도 다시 내려받아 같은 SHA256인지 배포 과정에서 확인합니다.

## 확인하지 않은 범위

Windows x64 시험판이며 코드 서명, 다른 PC의 최초 설치·AI 로그인, macOS·Linux 배포는 확인하지 않았습니다. 저장 형식은 기존 0.2.1~0.2.3과 같은 8입니다. 모든 연결 오류나 외부 명령의 성공을 보장하지 않습니다. 조회 범위 밖의 접수나 기록 파일 이동 등으로 확인할 수 없으면 접수 미확인 상태를 유지합니다. 입력이 저장되기 전 전체 프로세스를 잃은 경우의 직접 입력까지 복구를 보장하지 않습니다.
